Each section states the ground truth in the current code (with file references), what will change, and — in this project's tradition — which experiments have to be run against Logic before the design is trusted. Nothing here is speculative about the *current* code; everything about *Logic's* behavior that has not yet been observed is marked as an experiment.

## 1. Tempo honesty guards

**Ground truth.** Every bar→seconds conversion flows through one primitive, `barRangeSeconds` (`Sources/Logician/ToolHandlers.swift:92`), which does `(bar − 1) × beatsPerBar × 60 / tempo` with the tempo read once from the control bar (`Sources/Logician/AXTransport.swift:82`). The tools that *hand Logic bar numbers* — `logic_bounce_range`, `logic_set_cycle_range`, region tools, `logic_evaluate_change` methods `bounce`/`solo_bounce` — are already correct under any tempo map, because Logic does the interpretation. The tools that *slice audio themselves* — `logic_render_track`, `logic_evaluate_change` method `render`, `logic_record_midi`'s verification render — were silently wrong from the first tempo change onward. That asymmetry (a correct bounce next to an incorrect freeze-slice of the same bars) was the sharpest inconsistency in the behavior, and nothing warned about it. As of 2026-08-27 all three either refuse with the working alternative named or carry a `warning` with both tempo readings; the slices are still cut by constant-tempo math (making them *correct* is item 3), but they no longer claim to be something they are not.

**Smart Tempo raises the stakes.** Logic's [Smart Tempo](https://support.apple.com/guide/logicpro/smart-tempo-lgcp4e829ea1/mac) has a project tempo mode — **Keep** (recordings follow the project tempo, the classic behavior), **Adapt** (the *project tempo map is rewritten* to follow the recording), and **Auto** (picks one, leaning Adapt when the metronome is off and no tempo reference exists). Since Logic 10.4.2 this applies to **MIDI recordings too**. `logic_record_midi` streams a performance while Logic records — so on a project sitting in Adapt (or Auto that resolves to Adapt), the tool doesn't just *misplace notes*, it can **rewrite the user's tempo track** as a side effect, today, on a constant-tempo project. That is a destructive write no result currently mentions.

**Plan** (no new capabilities, pure honesty — ship before anything else):

- ~~**Smart Tempo write-protection.**~~ **PARTIALLY DONE** (2026-08-27) — the guard ships, the *read* it wants does not exist. Experiment 1 ran against a live Logic (read-only AX probe, FINDINGS 2026-08-27) and came back negative in a specific way: the **Project Tempo pop-up button IS in the control bar**, as a direct sibling of the `Tempo` slider inside the inner "Control Bar" group, but it publishes **no value at all** — `AXValue`/`AXTitle`/`AXValueDescription` absent, `AXDescription` empty, identifiable only by its `AXHelp` prefix `"Project Tempo menu"` — while the neighbouring Time Signature and Key Signature pop-ups do publish theirs. So the mode is **not AX-readable** today.

  What shipped: `logic_record_midi` reads the mode before arming and **refuses under Adapt and under Auto** (`precondition_failed`, nothing recorded, the fix named); when the mode is unreadable it records but attaches a `warning` saying the check went unverified and that an Adapt-mode project would have had its tempo map rewritten. `logic_get_transport` surfaces `project_tempo_mode` when known and `project_tempo_mode_note` (why not) when not — an unreadable mode is never reported as a value. `ProjectTempoMode` + `normalizedProjectTempoMode` carry the keep/adapt/auto mapping, unit-tested, ready for the day a read exists; those three branches are therefore **code, not observation**.

  🔬 Still open, and now the *whole* item: the button exposes `AXShowMenu`/`AXPress` and an empty `AXChildren`, so the likely read is "open the menu, enumerate items, look at `AXMenuItemMarkChar`" — a UI mutation on a read path called at the moment a recording arms, which is why it was not done blind. If the items also `AXPress`, experiment 2 (AX-*settable*) follows for free and the refusal upgrades to a guarded set-and-restore. Until then the honest state is: an Adapt-mode project is protected only if Logic ever starts publishing that value, and the unreadable case is a warning, not a guarantee.
- **Detect a non-constant tempo cheaply.** ✅ **Done** (2026-08-27). The control bar shows the tempo *at the playhead*, so `LogicAccessibility.sampleTempo` parks the playhead at the range's first bar, reads, parks at the last bar, reads, and restores — the position-dependence that made the bar math wrong is the sensor that detects it. Epsilon 0.05 BPM (below the slider's whole-BPM write resolution, above read noise; a disagreement that small moves a bar-33 boundary by ~27 ms). Every seconds-sliced result that is not refused carries a `warning` naming both readings and the tempo-safe alternative; a sample that cannot run degrades to a warning, never to a refusal, and the playhead is never moved when there is no position to restore (a failed restore travels with the verdict as `TempoSample.playheadLeak`). At most one sample per tool invocation — `logic_record_midi` now resolves tempo/meter once and shares one range and one sample between its scheduling math and its verification render; the bounce paths sample nothing. **Measured cost** (live, constant-tempo project): ~0.13 s per bar of playhead travel — 1.07 s for a 4-bar sample near the playhead, 14.25 s for playhead-to-bar-1 from bar 57. Live-verified only for the *constant* verdict and the playhead restore; the mismatch branches are unit-tested, since the test project has no tempo map and building one would have meant writing to the user's project.
- **Prefer the tempo-safe path when it exists.** ✅ **Done** (2026-08-27). `logic_evaluate_change` method `render` refuses with `precondition_failed` before anything is selected or written, naming `bounce`/`solo_bounce` — under a tempo map its two slices would cover different musical material, so the dB delta would be attributed to the plugin. `logic_record_midi` additionally refuses `speed > 1` on a mismatch: speed mode raises the tempo slider and writes a single BPM back, which cannot restore a map.
- **Guard the MCU timecode parse.** ✅ **Done, fail-fast only.** `timecodeBar()` assumed the 10-digit display is in beats mode; in SMPTE mode it silently read hours as bars. A pure classifier — `classifyTimecode` (`Sources/Logician/MCUMIDIRecording.swift`, 11 unit tests) — now judges the digits: the fixed field layout of the bridge's 10-byte buffer (bar 3, beat 2, division 2, ticks 3), refusal only on *positive* evidence (bars/beats/divisions are one-based in Logic, zero-based in SMPTE; blank division/tick fields tolerated), `ALERT` and the never-painted display as their own cases, and the decisive cross-check against the bar `setPlayhead` just parked at. Wired into the sync-critical consumers: `recordMIDI` and `recordVolumeAutomation` refuse with `precondition_failed` naming the fix ("press the SMPTE/Beats button in Logic's control bar or the MCU display to switch to beats"), and `timecodeBar()`/`timecodeBarBeat()` now return nil instead of nonsense, so polling loops time out with their own `verification_failed`. The string-compare-only sites (`MCURender`'s ALERT check, the vpot automation roll anchor) are mode-independent and untouched. **Still open:** the auto-fix. The bridge maps the `smpte_beats` button (`Sources/LogicMCUBridge/Bridge.swift:447`), and pressing it once, re-reading and continuing would need no restoration (the press *is* the fix) — but the press has never been verified against a live surface, and an unproven button press inside a sync-critical path is worse than a clear refusal; a TODO in `requireBeatsDisplay` points back at this bullet. The SMPTE digit pattern the guard rejects is also inferred, not observed: the next research session against Logic should log both displays' raw 10 characters and confirm the button's effect.
- **Fix the meter-blind `* 4` hardcodes** in `logic_record_midi`'s end-of-take math. ✅ **Done** (2026-08-27). Tempo and meter are resolved once, before the take is measured, and the measurement moved into `MCPServer.takeEnd` — pure, meter as a parameter, unit-tested (offbeats, partial bars, CC events, 3/4). The verification render and the scheduling math now agree by construction because they share one range.
- **`logic_set_tempo` under a tempo track**: ✅ **Done** (2026-08-27) — as a refusal, not a warning. It samples the tempo at the playhead and at **bar 1** (the project's first tempo node; a playhead already at bar 1 samples bar 2) and refuses with `precondition_failed` on a mismatch, naming the tempo track / Tempo List as where a map is edited. `tempo_sampled_at_bars` reports what was actually compared, because two agreeing points are evidence and not proof. Deliberately **no override argument**: "park the playhead and pass `expected_current_bpm`" would still be a single-slider write, and which node Logic edits — or whether it creates one — is unverified from here, so offering it would be a guess dressed as consent. Making that safe needs the same tempo-map read as item 3.

**Definition of done:** on a project with one mid-song tempo change, no tool returns silently wrong audio or writes to the tempo track — every affected result either refuses with the alternative named or carries a `warning`, `logic_health`-style. And `logic_record_midi` on an Adapt-mode project refuses instead of rewriting the tempo map.

**Where that leaves the item (2026-08-27).** The bar-math half is **shipped**: five of the six bullets are done, and every seconds-slicing path now either refuses with the alternative named or warns with both tempo readings. Two honest gaps remain, both blocked on observation rather than design:

1. **The Adapt-mode half of the definition of done is not reachable yet** — Logic publishes no value on the Project Tempo pop-up, so the Smart Tempo guard protects only readable modes and warns otherwise (first bullet). That is the last open piece of this item.
2. **The mismatch branches have never run against a real tempo map.** The two-point sample is live-verified for the constant verdict, the cost and the playhead restore; that a mid-song tempo change actually shows up as two different slider values follows from the control bar's observed position-dependence but has not been watched happening. A scratch project with one tempo change would close this in minutes — and would also be the first look at whether the slider publishes decimals, which is the case epsilon 0.05 was chosen for.

## 2. Stereo Out / master-chain addressing

**Ground truth.** The research is better than the roadmap line implied: Stereo Out, auxes, and bus channels **are ordinary MCU bank channels** (docs/FINDINGS.md:531 — the master chain sweeps like any track; the LCD shows `St Out`, and `lcdNameMatches` already matches it). The bridge even plumbs the MCU master fader end-to-end (`fader` accepts channel 0–8, state mirrors 9 faders — `Sources/LogicMCUBridge/Protocol.swift:355`), unused by the server. What blocks everything is one habit: every mixing/plugin tool calls AX `selectTrack(trackName)` first, which resolves against *track headers* — and output/aux strips have no track header, so they throw `trackNotFound` before the MCU is ever asked. `logic_survey_plugins` is the proof it can work: it alone falls back to the inspector strip (`Sources/Logician/AXPlugins.swift:305`) and surveys Stereo Out today.

**Plan:**

1. **Mixing first** (volume/mute/solo/sends): route output/aux/bus strips through `findChannel` → MCU without the AX `selectTrack` precondition; AX fallback goes through `anyInspectorStrip` (`Sources/Logician/AXHelpers.swift:11`) instead of the track-header path. Pan is AX-only today and follows the inspector-strip route.
2. **Plugins on the master chain**: replace the unconditional `logic.selectTrack` in the plugin tools (`Sources/Logician/ToolHandlersPlugins.swift:20, 50, 125, 234, 256`) with MCU channel selection (`selectFoundChannel`) when the name resolves to a headerless strip. The known wrong-channel failure (FINDINGS.md:1393 — plugins once landed on Stereo Out *by accident*) becomes the safety test: LCD-verify the PL view is showing the intended strip before any write, both directions.
3. 🔬 **Experiments before trusting the design**: (a) does MCU *selection* of an output-bank channel behave identically to a track channel (PL view, vpot pages, fader echo)? (b) is the dB calibration curve (`Sources/Logician/MCUAutomation.swift:96`) valid on the Stereo Out fader? (c) what exactly does the dedicated master fader (index 8) control vs. the Stereo Out strip fader — same object or not? (d) does Logic's `global_view`/Outputs view (button exists at `Bridge.swift:447`, never pressed by the server) give a more stable bank for outputs than scanning?
4. **Verification story**: A/B on the master chain already has a tempo-safe, master-safe path — `logic_evaluate_change` method `bounce` captures the full mix. Wire the new addressing into it and the "mix bus compressor A/B" workflow falls out for free.

**Definition of done:** `logic_set_volume`, mute/solo, and the four plugin parameter/add/remove/preset tools accept `Stereo Out` (and aux/bus names), verified by LCD echo, with the same compare-and-set semantics as tracks — and an agent can A/B a limiter setting on the master bus end to end.

## 3. Variable tempo (tempo track / Smart Tempo)

**Ground truth.** FINDINGS.md:712 already names the shape: *"tempo-track following in the bar math: read tempo changes, piecewise integration."* All the damage concentrates in the one primitive plus the two recording paths: `barRangeSeconds` and its four callers; `logic_record_midi`'s single linear ms ramp (`ToolHandlersTransport.swift:138`); automation recording's single `msPerBeat` (`Sources/Logician/MCUAutomation.swift:114, 399`). The bridge itself is tempo-agnostic (offsets arrive as ms) — no bridge changes needed.

**What Logic exposes on its side** (per [Apple's tempo documentation](https://support.apple.com/guide/logicpro/tempo-track-overview-lgcpc0ba44af/mac)): the tempo map lives in the **tempo track** (a global track) as tempo points, and two adjacent points can be joined into a **tempo curve** — a continuous ramp, not a step — so the integration below must handle both from day one. The same map is editable as rows in the **Tempo List** — reached at `View > List Editors`, Tempo tab; the floating-window-with-a-⌥⇧T-shortcut this line used to claim has **no menu item** in Logic Pro 12.3.1 (verified 2026-08-27) — and generated in bulk by the **Tempo Operations** window. Smart Tempo sits on top as the write-side: an Adapt-mode recording or import regenerates this map, which is exactly why the item-1 guard must land first.

**Plan, in dependency order** (all five shipped 2026-08-27 — see FINDINGS "Tempokartan läses ur Tempo List"; what is *verified* versus *unverified* is spelled out under "Where that leaves the item" below):

1. ✅ **Tempo-map acquisition — the Tempo List via AX.** Done, and the route turned out to be different from the guess: **there is no "Open Tempo List" menu item** in Logic Pro 12.3.1 (the ⌥⇧T floating window this roadmap assumed does not exist in the menus; Event List, Signature List and Marker List all have their own items, Tempo List does not). The way in is **`View > List Editors`**, which toggles a pane in the main window with an `AXRadioGroup` of four tabs described `Event`/`Marker`/`Tempo`/`Signature`; pressing `Tempo` reveals `AXGroup` desc `Tempo` → `AXScrollArea` → `AXTable`, three columns (`Position`, `Tempo`, `SMPTE Position`), and each row's text on its cells' child `AXGroup`'s **`AXDescription`** (`"1 1 1 1 "`, `"120,0000"` — decimal comma in a Swedish locale — `"01:00:00:00.00"`). `readTempoMap()` opens it, reads, restores the tab and closes the pane it opened: **2.03 s, no playhead motion**, versus 1.07–14.25 s of playhead travel for a two-point sample. Cached per project, 0.003 s warm. The open question about curves is **answered, negatively**: the Tempo List has no curve column, and `Additional Info` adds none — so a curve cannot be distinguished from a step by this route at all (see below). Playhead sampling stays as the fallback when the read fails; the MCU beats-display cross-check was not needed and was not built.
2. ✅ **Piecewise integration.** `TempoMap` carries tempo events at (bar, beat) with step and linear-ramp segments; `barRangeSeconds` takes it and integrates. Ramps use the **exact integral** — BPM linear in beats gives ∫60/BPM d(beat) = (60/k)·ln(b₁/b₀) — so there is no subdivision and no error bound to document for the math itself. A one-event map reproduces the old constant formula **bit-for-bit**, operation order included. Cached per project with the bank cache's scope discipline; invalidated by `logic_set_tempo` and by any recording whose Smart Tempo mode was not verifiably Keep.
3. ✅ **MIDI recording.** Per-event ms offsets are the integral of the map from the take's first bar line. `speed > 1` still refuses on a non-constant tempo — deliberately NOT softened: the map tells us the take's timing, not how to put a single slider write back, so the destructive-write reason is untouched by knowing the map.
4. ✅ **Automation recording.** Point placement, the pre-roll bar's own length, the ramp subdivision step and the per-point convergence budgets all integrate the map (each schedule entry carries the ms-per-beat in force at its own position). The bar-based playhead-chase verification is unchanged and is the proof.
5. ✅ **Docs + guide.** AGENT-GUIDE's "constant tempo assumed" passages now describe the map behavior, the two remaining rules (real-time recording; **constant meter**), and what the fallback still does. Tool descriptions updated where behavior changed.

The item-1 honesty guards remain the safety net underneath: when the Tempo List cannot be read, every affected path behaves exactly as it did before this item — warning or refusal, never a silent wrong slice.

**Definition of done — partially met, honestly.** The math and the plumbing are in and unit-proven; the *live* half of the definition still needs a project with tempo changes. On the user's constant-tempo project the read, the cache, the restore and the calibrated 8.000 s for bars 5–9 are verified live. What has never run against a real tempo map: a multi-row Tempo List (row grammar is verified for ONE row; the truncation cross-check against the list's own "Number of Items" exists precisely because a long table may publish only realised rows), a slice compared sample-for-sample against `logic_bounce_range`, and notes recorded across a tempo change.

**Still open, and now the whole item:**

- 🔬 **Curves are invisible to this route.** The Tempo List publishes Position, Tempo and SMPTE Position only, so a tempo *curve* is read as a step. The map therefore reports `curveUncertaintySeconds` — the exact difference between integrating each adjacent pair as a step and as a ramp — and the warning names it in ms when a range could be affected. Closing this needs another source for the curve flag: the **tempo track** itself (a global track; are curve handles AX-visible?) or the Smart Tempo Editor. Until then, a ramping project's boundaries carry a quantified caveat rather than a guarantee.
- 🔬 **Multi-entry grammar and the mismatch branches** are unit-tested against captured strings, not observed. A scratch project with two or three tempo points (one of them a curve) would confirm the row grammar, the item-count cross-check, and — as a bonus — whether the control-bar slider publishes decimals, which the 0.05 BPM epsilon was chosen for and has still never seen.
- **Meter is the last assumption.** Signature changes live in their own list (the Signature tab of the same List Editors, which *does* have its own menu item: `Window > Open Signature List`), and reading them is the natural follow-up — the same acquisition pattern, one tab over.

## 4. Plugin preset browsing

**Ground truth.** Today's `logic_plugin_preset` is relative-only stepping via the *"Next/Previous Plug-in Setting for topmost Plug-in Window"* key commands, verified by an AX popup label that opaque plugin UIs don't expose (`Sources/Logician/ToolHandlersPlugins.swift:117`). The vpot-browse-and-press primitive the roadmap line dreamed about already exists **twice** — the plugin browser (`Sources/Logician/MCUPluginBrowser.swift:14`) and the send-destination browser (`Sources/Logician/MCUSends.swift`) — with settle/reverify/wrap-detection solved. What does *not* exist is any recorded observation of an MCU view that lists presets: no LCD grammar, no assignment code, nothing in FINDINGS.

**Plan:**

1. 🔬 **Research session first** — two questions against Logic: (a) does the MCU plugin-edit view expose a preset/Setting item anywhere (vpot page, NAME/VALUE toggle)? Log the LCD grammar if so. (b) The AX route we *know* exists: the plugin window header's preset popup menu (FINDINGS.md:906 observed prev/next buttons and a menu) — can the menu be opened and its items enumerated the way other AX menus are (`Sources/Logician/AXBounce.swift:190` does exactly this for the Bounce menu)?
2. **Ship whichever is real** (AX menu route is the likely winner; the vpot route only if (a) pans out): `logic_plugin_preset` grows `list` (enumerate names) and `name:` (jump directly, verified by the label read that already exists). Relative stepping stays as the fallback for plugins whose preset UI is opaque — with today's honest `stepped: false` when nothing can be verified.
3. Master-chain presets come along for free once item 2 lands, since the blocker is the same `selectTrack` gate.

**Definition of done:** an agent can ask "what presets does this compressor have?", jump to one by name, and get an honest failure on plugins that expose nothing — no blind stepping loops.

## 5. Homebrew packaging

**Blocked on the repo going public** — a formula needs a public URL to fetch. When that happens, the shape is standard and small:

1. Tag releases (`v0.50.0` — the version already lives in `Sources/Logician/Support.swift`).
2. A tap repo (`BanneBanning/homebrew-logician`) with a formula that fetches the release tarball and runs `swift build -c release` (build-from-source; `depends_on :macos` ≥ 13 and the Xcode CLT).
3. README install step 1 gains the alternative: `brew install bannebanning/logician/logician`.

Honesty note, same as the install badges: Homebrew replaces the *download & build* step only. The Mackie Control setup and the Accessibility grant are Logic- and macOS-side by nature — no package manager reaches them; `logic_health` remains the doctor.

Not planned: npx/uvx/Docker distribution — Logician is a native Swift binary that must talk to CoreMIDI and Accessibility on the host; a container cannot.

## Parked

- **Localization** (English Logic UI). Scoped during this planning round so the parking is a decision, not an oversight: there are *three* independent English-string surfaces — the centralized key-command table (24 entries, plus 14 leaked inline literals), ~70 scattered Accessibility literals across 10 files, and ~25 MCU LCD literals across 7 files that the old "Accessibility string matching" framing didn't even count — plus locale-sensitive formats (`"Track N “Name”"` parsing, `"dB"` suffixes, `-oo`). Real support means two string tables and a test pass per language against a live localized Logic. Parked until there's a second-language user to test with; the v1 assumption stays in the README.
- **Track-stack freeze rendering** — a Logic limitation, not ours; `solo_bounce` covers stack subtracks and the freeze refusal already names it. Stays a documented limitation.
